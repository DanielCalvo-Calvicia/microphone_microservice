## Goal

The runtime requirements hold only what the service needs; the tools to test and lint it are in a separate file; versions have lower bounds (the workspace convention, `deployment/docs/DEPLOYMENT.md` section 3).

## What it must do

1. `requirements.windows.txt` and `requirements.linux.txt` (they are identical today) keep: `fastapi`, `uvicorn`, `sounddevice`, `numpy`, `-e ../shared-logging`, and the bundled `./vendor/contracts_microservice-<version>-py3-none-any.whl`. Add lower bounds with `>=`, taking as the bound the version installed and working in the service venv on 2026-11-05 (fastapi 0.136.1, uvicorn 0.47.0, sounddevice 0.5.5, numpy 2.4.5) unless a lower one is known to work; do not use ranges or `==`.
2. Create `requirements-dev.windows.txt` and `requirements-dev.linux.txt`: `-r requirements.<platform>.txt` then `pytest`, `httpx` (the tests need `TestClient`), `ruff`, `black`, `mypy`, with lower bounds from the installed versions (pytest 9.0.3, httpx 0.28.1, ruff 0.16.8, black 26.5.1, mypy 2.3.1). `pytest-asyncio` is installed in the venv: check whether any test needs it (`pytest.ini` has no asyncio mode); add it only if it does.
3. Keep the comments that explain the `shared-logging` and `contracts` lines.
4. **Check the deployment tool before changing anything:** search `deployment/` (scoped to its folder, not the workspace) for how it installs `requirements` and whether it runs tests or needs the dev tools; the catalogue's `requirements = { windows = ..., linux = ... }` must keep pointing at the runtime files. If the tool needs a change, stop and ask (T-03.3 style); do not edit `deployment` here.
5. Update the venv instructions: `CLAUDE.md` (Commands: how to install the dev tools), `README.md` (Run: runtime; Test: dev), `docs/deployment/deployment.md`, `docs/security/security.md` (supply chain), `docs/setup/09_technology.md`, risk 4 of `docs/setup/14_risks-and-debt.md`, `docs/architecture/architecture.md` section 12 item 6.

## What it must not do

- Reinstall or modify the service venv (`windows\`); only note the command.
- Bump `contracts` or `shared-logging`.
- Touch `.env*` files.

## Files

`requirements.windows.txt`, `requirements.linux.txt`, `requirements-dev.windows.txt` (new), `requirements-dev.linux.txt` (new), `CLAUDE.md`, `README.md`, `docs/deployment/deployment.md`, `docs/security/security.md`, `docs/setup/09_technology.md`, `docs/setup/14_risks-and-debt.md`, `docs/architecture/architecture.md`, `docs/proposals/PR-002-dotenv-and-requirements-split.md` (dated note for item 2 and 3 of the proposal).

## Verification

In a throwaway venv created in the scratchpad (not the service venv): `pip install -r requirements.windows.txt` succeeds and `python -c "import fastapi, uvicorn, sounddevice, numpy"` works; `pip install -r requirements-dev.windows.txt` adds the tools; the service's own `pytest`, `ruff` and `mypy` still pass in its venv. Say that the Linux file was not installed on Linux.

## Acceptance

Both runtime files have no dev tool; both dev files exist and include the runtime file; every package has `>=`; the documents agree; nothing outside the files listed changed.
