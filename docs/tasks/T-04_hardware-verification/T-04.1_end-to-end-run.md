## Goal

Confirm that the real sounddevice adapter, the negotiation, the utterance cutting and the stream work together on the Windows machine with the microphone.

## Steps for the maintainer

1. Make sure nothing else listens on port 8000 (the script boots its own server there). From the service folder, with the service venv: `& windows\Scripts\python.exe tests\simple.py`. It is a smoke test: it checks `/health` and `/available`, calls `/start`, reads `/stream` for `STREAM_READ_SECONDS` (2 s), calls `/stop` and checks the availability again. It does not judge the cutting; note whether every step passes and which device was chosen (see the log).
2. For the cutting, start the service (`python main.py`), call `POST /start`, read `GET /stream` (for example `curl -N http://127.0.0.1:8000/stream`) and say three short sentences with a clear pause between them (longer than `MICROPHONE_SILENCE_LIMIT_SECONDS`, 2 s by default), then stay silent for a few seconds; call `POST /stop`. Each `utterance` line is one phrase: its `bytes_base64` is long, so count the lines instead of reading them.
3. Repeat once with the room noise you normally have (fan, music, a TV low).
4. Note: how many `utterance` events arrived, whether each sentence was one utterance, whether the start of a sentence was clipped, whether an utterance never ended, whether `/stop` released the device (the microphone icon of Windows goes off) and whether `/available` answered `is_available: true`.
5. Try `MICROPHONE_TARGET_KEYWORDS` with a word of another input device name, if there is one; note which device was used.

## What the assistant does

Before: runs the unit tests, ruff and mypy so a failure is not a code problem, and prepares the checklist above. After: records the *Results* below, and if something failed, opens a task (not a silent fix) with the observation.

## Result (2026-11-10, run with the maintainer at the PC)

**Machine and device:** this Windows PC; PortAudio input device index 1 (the OS default), the headset microphone "Auriculares con micrófono (FORGEON Captain)" (MME, 1 channel, default rate 44,100 Hz; the service asked for 16,000 Hz, logged `Requested sample rate may not be supported by the device` and opened it at 16,000 Hz anyway). Run from a scratch copy of the working tree with a made-up `.env` (port 8101, `MICROPHONE_BACKEND=real`), never the real `.env`; the real microphone was opened five times in all, with the maintainer present and a "go" before each; **nothing was recorded to disk**: the scripts computed only lengths, peaks and RMS in memory.

**Smoke test `tests/simple.py`:** the real device opened, 375 chunks (768,000 bytes, 0 overflows) were read, `/stop` answered 200 and the device was released. It reported **2 of 7 checks passed**, and the five failures were the **script's, not the service's**: it still expected raw `partial` audio events (the stream carries `stream_started` and `utterance` since the cutting moved here on 2026-10-05, so a 2 s read of a quiet room legitimately gives no audio), it compared the `{"is_available": ...}` envelope with a bool, it expected `/available` to be false before the start and after the stop (it is a probe of the device and is true whenever one exists), and it read the JSON of `POST /start` as a stream. Fixed in `tests/simple.py` (it now checks `is_available`, the JSON of `/start`, that `/stream` gives `stream_started` and prints each utterance, and its server stops within 5 s like `main.py`); it passes **7 of 7 on the simulated backend** (`MICROPHONE_BACKEND=sim`, no device) and was **not re-run on the real microphone** after the fix. ruff and mypy stay clean, 171 tests.

**The cutting, through the real service's `GET /stream` (45 s, three sentences about 6 to 10 s apart, one beep as the start cue):** `stream_started`, then **three `utterance` events, one per sentence**, arriving at 10.2, 18.2 and 26.1 s after the start, **7.42 s, 5.38 s and 4.93 s long** (peak 27,305, 20,711 and 22,209 of 32,767, RMS about 1,700 to 1,900: loud, not clipped), then `completed` on `/stop` at 45.3 s; 707 chunks, 0 overflows; `/available` true before and after; the process was terminated by the script and the device was free for the next run. No utterance failed to end. The utterances are longer than the speech: each one carries the 2 s silence limit plus the 1.4 s the smoothed volume needs to fall under the end threshold, about 3.4 s of trailing silence, so a sentence reaches Brain at least 3.4 s after it ends (finding F10, now measured on a real microphone). **The service's own adapter and cutter, run in-process (40 s, a diagnostic with a per-2-s loudness print):** speech started an utterance within a chunk or two (raw RMS 2,700 to 5,900 against a start threshold of 300), the room noise between sentences was RMS 4 to 80, and four utterances of 7.68, 6.34, 5.25 and 4.86 s were cut. A direct level check of the device (12 s, nothing kept): speech at RMS 1,000 to 4,000 with peaks to 15,800, silence at RMS 4 to 20.

**A false start, so nobody repeats it:** the first 60 s HTTP run produced no utterance at all although the maintainer spoke. It was **my reading script's bug** (a socket-timeout hack that broke the chunked read), not the service: with a reader thread the same service cut the three utterances above.

**Not judged, and why:** whether the **start of a sentence was clipped** (nothing was recorded, and the pre-roll of 0.2 s is there to prevent it; T-04.2 has the offline method), the **noisy-room repeat** (step 3 of the plan), another input device through `MICROPHONE_TARGET_KEYWORDS` (step 5), and whether the Windows microphone indicator went off after `/stop` (not observed). The scratch copy and its logs (no speech) were deleted, nothing was left running, ports 7998 to 8005, 8000 and 8101 are free.
