## Goal

Build the microphone image from a scratch deployment and record how long it takes and how big it is.

## Read first

The rules of [T-07](T-07_docker-and-arm64-acceptance.md), `deployment/docker/service.Dockerfile`, `docker_runtime.prepare_context` (the build-context filter: `.env.*` except `.env.example`, `testclear/`), stt's [T-03.1](../../../../stt_microservice/docs/tasks/T-03_docker-and-arm64-acceptance/T-03.1_amd64-build.md).

## Files

None changed. Scratch folders only.

## Steps

1. With the maintainer's yes, make the scratch deployment of the rules and run `oblivion.py deploy --host robot -s microphone --dry-run` first, then without `--dry-run` (this builds: network, a few minutes).
2. Record: the build time, the image size (`docker --context desktop-linux images`), the base image, the apt packages that were installed (`libportaudio2`, `portaudio19-dev` are in the catalogue list: with the lazy import of T-02.3 `sim` does not need them, so say whether the image still carries them and what that costs in MB).
3. Look at the build context the tool made: no `.env`, `.env.staging` or `.env.production`, no `windows/`, no `.git` (names only).

## Acceptance criteria

The image builds; the number of MB and the build time are recorded; the build context holds none of the excluded names.

## Verification

The build output (no secret in it), `docker images`, the context listing, in *Notes*.

## Notes

If the tool refuses Docker for an audio service on Windows (F7) and T-06.4 is not built, the build is done by hand with the same Dockerfile; say so in *Result*.

## Result (2026-11-10)

Run with the maintainer's "go". Docker Desktop 29.5.2, linux/amd64, `--context desktop-linux` (through `DOCKER_CONTEXT` for the tool). Scratch deployment: a git repo made from a copy of the working tree (no `windows/`, `.git`, `.env`, `.env.staging`, `.env.production`, caches; commit `64afe44`), a scratch config folder (the catalogue with absolute library paths, `services/`, one machine with the microphone only, `local/microphone.toml` with `git`, `branch` and `runtime = "docker"`, and **nothing** for the backend), the maintainer's `config/local/` untouched. `oblivion.py validate` accepted `runtime = "docker"` for a microphone on a Windows host (the `sim` preset) and `oblivion.py env` showed `MICROPHONE_BACKEND=sim` from the layer `catalogue`. A `--dry-run` cannot go past the clone of a scratch repo ("no requirements file to build the image from"), so the real deploy was the first run. **Build:** `deploy` took **41 s** in all (base image cached; the pip step 12 s). The `docker build` line: `--build-arg APT_PACKAGES=libportaudio2 portaudio19-dev` and no `PREPARE`; `RUN if [ -n "" ]` for the prepare step 0.3 s; **0** matches for `Building wheel` (binary wheels only); installed: fastapi 0.136.1, uvicorn 0.47.0, python-dotenv 1.2.4, sounddevice 0.5.5, numpy 2.4.5, contracts-microservice 0.16.0, `shared-logging 0.1.0` from `libs/`; Python 3.12.16. Image `oblivion/microphone:local` **317 MB** (`docker images`); layers: pip install 93.4 MB (numpy), apt install about 7 MB (`libportaudio2 portaudio19-dev`), the copy of the tree 1.2 MB: PortAudio in a `sim` image costs little, so the catalogue's per-service `apt` list stays. The build context held no `.env*` (the only such name in the image tree is `.env.example`). The `docker run` line: `-p 127.0.0.1:8000:8000`, the `.env` as a read-only bind mount at `/app/.env`, no `--device` (a simulated microphone needs none). The deploy output ended with `microphone: healthy and available, warning: simulated microphone (MICROPHONE_BACKEND=sim): a generated signal, not a real device`: the readiness check passed without a device, which is the audit's problem 2 fixed end to end.
