> The workspace rule: `deployment/` is its own repository and has its own `CLAUDE.md`; read it before editing. Ask the maintainer before touching another repository, and do not commit there.

## Goal

Show that a machine without a microphone can be deployed and run the pipeline on `sim`, and keep the deployment documents true.

## What it must do

1. **Preset (decided in T-02.1):** if the maintainer wants a layout that starts on `sim`, add `MICROPHONE_BACKEND = "sim"` under `[services.microphone.env]` of the catalogue (as stepper does with `MOCK_HARDWARE = "1"`), and say in `config/local/microphone.toml` documentation that the machine with the sound card sets `real`. If the maintainer wants no preset, skip this step and say so in the Resolution.
2. Regenerate `deployment/config/services/microphone.toml` with `brain_microservice\windows\Scripts\python.exe deployment\scripts\env_inventory.py --write`.
3. Update `deployment/docs/DEPLOYMENT.md` (the microphone variable table).
4. Add a test in `deployment/tests/` that a layout with `MICROPHONE_BACKEND=sim` passes the readiness check without a device (the check reads `/available`; use the existing fakes of `http_health`).
5. Run the full pipeline check from the workspace root: `brain_microservice\windows\Scripts\python.exe -m pytest contracts\tests -q`, and the `deployment` suite (about 140 s).
6. Optionally, an end-to-end run with the real microphone service on `sim` instead of the fake `SineStream`: only if the maintainer asks.

## What it must not do

- Change the code default of the service.
- Edit `.env` files, the venvs or generated `contracts` folders.
- Commit or push in any repository.

## Acceptance

The `deployment` and `contracts` suites pass; the catalogue, the generated toml and the manual agree with `.env.example`; this repository's `docs/deployment/deployment.md` and `docs/security/security.md` (a simulated device is not a security feature) mention the preset if one exists.
